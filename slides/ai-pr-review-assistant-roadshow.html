Why

为什么做

PR Review 第一轮成本高、信息碎、容易漏重点

核心痛点

  1. 变更上下文分散，Reviewer 需要先手动筛重点。
  2. 大 PR 文件多，关键风险容易被淹没。
  3. Review 质量依赖个人经验和时间状态。

AI 直接总结的问题

  1. AI 直接总结容易黑盒，缺少依据和过程。
  2. 有价值的 Review 必须给出风险、原因和建议。

03 / 12

Solution

解决思路

把 AI Review 从“一次性回答”改成“受控流程”

为什么这样设计

  1. 不是直接让模型总结整个 PR。
  2. 而是拆成可追踪的多个步骤。
  3. 模型负责分析，系统负责上下文、状态和约束。

想达到的效果

  1. 每一步都能展示给用户。
  2. 每一步都能被后端校验。
  3. 目标不是更像聊天，而是更像真实 Review 过程。

核心原则：可视化、可追踪、可复核、可约束。

Engineering

工程实现

把设计思路落到具体系统

核心实现

  1. PR URL 解析：提取 owner / repo / pullNumber。
  2. GitHub 数据获取：metadata、changed files 和 patch。
  3. Review Context 构建：整理 PR 信息、文件 diff、统计和 warning。

系统落地

  1. Review Pipeline 编排：串起 context、loop、result 和状态流转。
  2. SSE 流式反馈：把阶段、动作和结果实时推到前端。
  3. 前端工作台：统一展示 PR、Diff、Timeline、风险和建议。
08 / 12

Core Design

上下文构建

先治理输入，再交给模型

Context 包含

  1. PR 标题、描述、作者、分支、状态。
  2. 文件名、状态、增删行、patch。
  3. totalFiles、includedFiles、ignoredFiles、largeChange。
  4. truncated / ignored / warning 标记。

上下文策略

  1. 过滤 lock、dist、build、minified 文件。
  2. 单文件 patch 超长截断。
  3. 大 PR 标记 warning，优先做风险文件筛选。

目标：减少噪音、控制 token、保留关键证据。

10 / 12

Accuracy

误报漏报控制

准确性不只靠 prompt，而是靠系统约束

降低误报

  1. 风险必须来自已 inspect 文件。
  2. 风险必须由 diff 支撑。
  3. suggestion 必须绑定已有 risk。
  4. 忽略低价值文件，减少噪音。

降低漏报

  1. 小 PR 尽量检查全部文件。
  2. 大 PR 优先检查高风险文件。
  3. 关注安全、鉴权、API 边界、数据模型、异常处理、删除逻辑。
  4. 0 风险结束前触发二次复查。
  5. 有风险无建议时强制补充建议。
